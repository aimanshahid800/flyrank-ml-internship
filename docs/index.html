Abstract. This study asks which pages in a content portfolio most need a refresh, and whether a simple age/position rule is enough to answer that question. A rule-based baseline scored AUC 0.494 (chance-level) against a measured decline label, so a Random Forest model was trained instead, reaching AUC 0.760 under a grouped, leakage-audited validation split. The model surfaced a non-obvious, actionable pattern: many top-priority pages are not stale — they already rank well but suffer from low click-through, pointing to snippet/title fixes rather than content rewrites. The resulting ranked queue is 3.5x more reliable than the rule baseline (11.3% vs 41.1% low-confidence picks) and is intended as decision-support for editorial review, not an automated or causal claim about search performance.

01Problem framing

The decision this supports

Content editors managing large page portfolios need a repeatable way to prioritize which pages deserve a refresh this cycle — manual review of thousands of pages doesn't scale.

The case study: this mirrors a real bottleneck at FlyRank, which runs content as infrastructure for clients — researching, publishing, and optimizing pages against live search data. Its product already flags declining pages today, but with hand-written, if-this-then-that rules (a health score, quick-win tags) rather than a trained model. Those rules work, but on messy, tangled search signals they run out fast. This capstone asks the next question directly: can a learned model beat that fixed rule at picking which page to fix first?

Unit of analysis: individual content page (content_id). Output: a decline-priority score and ranked action label — refresh_now, monitor, or no_action. Action taken: an editor reviews and refreshes the highest-priority pages first.

Cost of a wrong call: a false refresh_now wastes editor time on a page that wasn't declining; a false no_action lets a genuinely declining high-traffic page keep losing visibility, unnoticed. Why ML at all — the baseline rule (age + position gap) tested at chance-level, so a learned model was needed to find real signal.

02Data safety

What went in, what was left out

Source: content_refresh_anonymized.csv (30,000 rows), derived from the FlyRank/internship-warehouse release — fact_content_daily_performance (month = 2026-03) + dim_content.

Features used: content_age_days, impressions_last_30d, avg_position, ctr.

Deliberately excluded: GA4 session data (only 4.2% availability), every client-identifying field, raw domain/URL/query strings.

Leakage check

No hard leakage found. One caution flagged: impressions_last_30d partially overlaps with how trend_direction — and therefore the label — is itself defined, since trend is calculated from 30-day impression change. This is a definitional overlap, not future-data leakage. content_id is used only for grouping in the split, never as a feature.

Confirmed: no client names, domains, or private queries appear anywhere in the working repo.

03Baseline

A rule, tested honestly, and it lost

Built first: score = 0.6 × age_score + 0.4 × position_gap_score, producing reason codes (stale_content, position_opportunity, low_priority) and the same three action labels used throughout. Tested against the identical label and data as the model.

Baseline rule
0.494
Random chance
0.500

Effectively indistinguishable from chance. This is a fair, honest negative finding, not a failure: age and position-gap alone don't predict decline in this dataset, and reporting that clearly is what motivated the modeling work that follows.

04Model / analysis

Random Forest, on four honest features

Method: Random Forest (200 trees, max depth 8, balanced class weight) — chosen for handling non-linear feature interactions and for giving interpretable feature importances.

Target: is_declining = 1 if trend_direction == "down" (a >10% impression decline, 30 days vs the previous 30) — a proxy for real-world decline, not verified ground truth.

Left out on purpose: GA4-derived engagement fields, due to low coverage across the portfolio.

Key finding

Top-priority pages in the ranked queue are not primarily old or stale — they're high-ranking pages (position #1–3) with low CTR. low_ctr is the single largest reason code: 1,663 of 3,108 refresh_now picks. This runs against the naive assumption that "refresh" means "rewrite old content."

Negative result, stated plainly: the baseline rule's core assumption — that age and position gap predict decline — does not hold in this dataset. A well-understood "no effect" is a valid result, not a failed one.

07Recommendation

What an editor does with this tomorrow

Full ranked queue: 30,000 pages scored — 3,108 refresh_now, 19,646 monitor, 7,246 no_action.

Start with refresh_now picks tagged low_ctr — fast wins (title/snippet fix, not a full rewrite) on pages that already rank well.

41.1%

Share of top-priority picks with <10 impressions (low-confidence, noisy signal) — model picks are meaningfully more trustworthy.

Always review

Top 20 picks, every cycle

Spot-check against page content before assigning editor work. Same for any pick under 10 impressions, or a low_ctr tag on an already top-3 page — may be a snippet issue, not a content problem.

Never automate

Auto-publish, or silent deprioritization

No auto-publishing off model output. No dropping no_action pages without a manual check — false negatives exist. No using this output as sole justification without human-verified traffic data.

Confidence: directional and decision-support only — not causal, not validated beyond this single-month sample.
